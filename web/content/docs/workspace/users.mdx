description: "A project's Users page: every end user its agents served in the window, by the id the application tagged runs with, with their traces, errors, steps and tokens — narrowed by the trace list's filters, a page at a time, downloaded as CSV or JSON, each opening their traces."
---

A **user** is whoever your agents served: the person a run was for, as the
application named them, never a member of your organization. A project's
**Users** page lists every one seen in the window with what their runs added
up to, and each opens their traces together. Everything on it is metadata,
and the id is as stored: hashed under the project's own key, so the page names
nobody by it.

## Naming the user

Name the user when you open a run — `user_id` in the [SDKs](/docs/api/sdks)
(`userId` in TypeScript, `UserID` in Go), `user.id` on the span, which is OpenTelemetry's own name for it — and every
span inside the run carries it. A run that names no user is nobody's and counts on
no row here; a project whose runs name none sees the page say so, with the
attribute to set.

## The list

Every user seen in the window, the most tokens first, fifty to a page, laid
out as the [trace list](/docs/workspace/traces#the-list) is:

| Column | What it is |
|---|---|
| User | The user's id, as stored; opens their traces |
| Traces | How many runs were for them in the window |
| Errors | How many of those had a span that failed |
| Steps | The steps those runs took, summed |
| Tokens | Their model calls' input and output tokens, summed; hover for the split |
| First seen | When their first run in the window started, in your time zone |
| Last seen | When their last run in the window ended |

**Columns** shows or hides each of these, and the input and output tokens
apart, the counts and the tokens each a group under its own heading; the
user's id always shows. Your columns, and how tightly the rows sit
(**Row density**, the same on every list), are kept in your browser rather
than in the page's link.

### Filters

The **Filters** panel beside the list is the
[trace list's](/docs/workspace/traces#filters): each agent, status, model,
tool, user, session, environment, release, tag and prompt among the window's
runs, with how many users had a run carrying it — counted under every other
filter. A user is listed when one of their runs passes the filters, and the
row still sums every run of theirs in the window: a model lists the users
with a run that called it, each with all their runs. A user's id can be
typed in as well (**Text**), as the User column shows it, to find one. The
filters in force stand above the rows: clear one with its ×, or all of them
at once.

### Sort, pages and the window

**Sort** by any column by clicking its heading; a second click turns it
round. Ids and first seen sort the alphabet's and the calendar's way; the
most and the latest come first on the others.

**Rows per page** is 25, 50 or 100; beside it, the total the filters admit,
and the way to the first, previous, next and last page.

**The window**, beside the page's title, is the last day, week, 30 or 90
days, by the day each span arrived. The page reads the spans within it —
never the whole table — so a user whose runs have all passed their retention
is no longer listed. A window of more runs than the store sums at once,
about a million, shows the page as unavailable, and one of more than about a
hundred thousand lists its users without the filters' values; a shorter one
reads. **Refresh** beside it reads the list now; and beside
that, have the page read itself again every 30 seconds, minute, 5 or 15
minutes as well.

The list draws itself again as the project's runs land, while it is in view:
at once for the first, and once more for whatever arrives in the next 30
seconds.

Every filter, the sort, the window and the page are in the page's URL, so a
link holds the view.

### Downloading the list

**Download** writes the list as a file, CSV for a spreadsheet or JSON: every
user its filters admit, sorted as it is, up to the first 10,000, each with
their id as stored. A file holds what the list holds — metadata — and never
a message.
